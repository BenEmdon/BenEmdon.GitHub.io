Indexing the commit cloud

October 2026

This series is about one thing: how we get to the next magnitude of agent scale.

Thesis

In a commit-cloud architecture, a commit lives on the server the moment it is created. So every index we need, search, code intelligence, blame, can be computed right then, for every change, merged or not. Code intelligence stops being a batch job over main and becomes a property of every commit. That is how we get to the next magnitude of agent scale.

Where we are

Our code search leans on Sourcegraph, an external system that has to be fed from the outside. Indexes are built for merged code, on a schedule, by pipelines that live outside source control. The consequences are predictable. Search results lag main. Precise navigation, jump to definition, find references, exists only where an index happened to be generated and uploaded. And open changes, the work actually in flight, get neither. A reviewer looking at an unmerged change is navigating with a stale map. Agents have it worse: they consume code intelligence programmatically, and the index they query describes a repo that no longer exists. We want off Sourcegraph for code search, and swapping in another external indexer bolted onto the side of source control repeats the same structural mistake.

The bet

Indexes are derived data. That is the core move in part 1: everything that is not the changeset itself, blame, path history, ancestry, is derived data, computed from the commit, recursively, eagerly or lazily, and cached behind an API.1 The mechanism generalizes past what Anthropic described. The search index is derived data. The SCIP index is derived data.2

In a commit cloud, the commit is born on the server, so index generation starts the moment the commit exists:

  • Post-commit, not post-merge. The trigger is commit creation, not landing. Open changes get indexed on the same footing as main.
  • Incremental and content-addressed. Only the files a change touched get re-indexed. Results are keyed by content, so a rebase or a restack reuses most of the parent’s index instead of starting over.
  • Two index families, one mechanism. A text search index for fast search across any revision, and a SCIP index for precise navigation: jump to definition, find references, the language-server-grade answers that text search cannot fake.
  • Eager where it is hot, lazy where it is cold. Main and open changes index immediately. Deep history computes on demand and caches.

The payoff lands in review first. Jump to definition on the exact change in front of you, not on last night’s main. Then it lands everywhere else: agents planning a change can search the world as it will look with their change applied, because that world already has an index.

What we build

  1. A derived-data indexing service inside source control: post-commit triggers, content-addressed index storage, incremental computation as the default.
  2. SCIP generation per change for our main languages, so review tools and editors get precise jump to definition on any revision, merged or not.
  3. A search index per revision, owned by source control itself, so code search can target any commit and Sourcegraph can be retired for code search.
  4. A freshness policy consumers can rely on: eager indexing for main and open changes, on-demand for cold history, and explicit staleness signals when an index is not ready yet.

Open questions

  • Cost and retention: indexing every change is real compute. What is the TTL on indexes for abandoned changes, and who pays for the fan-out.
  • How much index reuse actually survives a rebase. SCIP is compiler-backed, so reuse may be strong for text search and weaker per language for precise indexes.
  • Indexer ownership: per-language SCIP indexers owned centrally by one platform team, or by the language communities that know the compilers.
  • Demand: do users and agents truly search arbitrary revisions, or is main plus open changes enough to cover nearly everything.

2. SCIP, the Source Code Intelligence Protocol, a language-agnostic format for precise code navigation (go to definition, find references): deepwiki.com/sourcegraph/scip ↩
