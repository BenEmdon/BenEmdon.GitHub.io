Merge-time code mods

October 2026

This series is about one thing: how we get to the next magnitude of agent scale. This part is written under two assumptions: every change lands by rebasing onto main, and a commit cloud exists, which part 1 argues for.

Thesis

When landing is a rebase and every commit lives in the cloud, a code mod stops being a pull request entirely. It becomes a script the system runs inside the landing rebase: once on main, and once on every open change the mod touches. The cross-cutting change lands everywhere at once, and nobody has to rebase out from under it. That is how we get to the next magnitude of agent scale.

Where we are

A code mod today is a really large pull request. It goes through the merge queue, someone times it for a quiet window, and everything queued behind it breaks, because a massive cross-cutting change just rewrote the ground every open branch was standing on. Two pieces of the future make that whole shape unnecessary. The first is the commit cloud from part 1: commits are born server-side and stay there, so the system can see and compute over all of them. The second is the landing model: no merge commits, every change merges by rebasing onto the tip of main. Given those two, the code mod problem changes completely.

The bet

  • Landing is already a computation the system performs. Every change lands by rebasing onto main’s tip, server-side. A code mod hooks into that computation. When a mod lands, the system runs its script against the current tip and commits the result. No stale snapshot from when the author started work, no quiet window to aim for.
  • The cloud can see every open change. It knows each change’s diff, so it can select exactly the changes whose files intersect the mod’s surface and run the script on each one, in parallel, server-side. Each change is rewritten in place under the same change ID, so stacks and descendants follow automatically.
  • Then the rebase does the rest. An open change that already carries the mod rebases onto the new main cleanly, because the mod is present on both sides. The breakage that used to surface one author at a time, over days, mostly never happens.
  • What cannot be applied cleanly gets flagged on the change itself, with the script’s output attached, and the author or their agent repairs it. That change cannot land until it takes the mod. That is the correct incentive: the mod is not a suggestion, it is part of the ground everyone stands on.

The rebase framing is the stronger one. There is no merge driver analogy, because there are no merge commits. There is no separate fan-out step across branch heads, because the cloud already holds every change. And targeting is by intersection, not by brute force across all branches.

What we build

  1. A landing pipeline where the rebase is a server-side, scriptable step, with code mod scripts as a first-class hook in it.
  2. Change selection by intersection: the system computes which open changes a mod touches, from the cloud’s view of every change’s diff.
  3. In-place rewrite semantics with stable change IDs, so applying a mod to an open change does not fork its identity or break its stack.
  4. Per-change result reporting, and a repair loop for changes the script cannot apply cleanly, blocking their landing until resolved.

Open questions

  • Concurrency: two mods landing minutes apart, selecting overlapping changes. What order do they apply in, and does the second mod’s author see the first already applied to their selected changes.
  • Determinism: the script has to produce the same result on main and on an open change, or the present-on-both-sides trick fails and the conflicts come back.
  • Who can ship a mod: a script the system runs across the whole cloud is the highest-impact change class we have. Agent approvals (part 2) gate it, but what review of a script actually looks like is an open design problem.
  • Cost when the intersection is nearly everything: a truly global mod still pays one run per open change. Parallelism helps. It does not make it free.
