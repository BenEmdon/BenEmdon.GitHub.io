Solving source control

October 2026

This series is about one thing: how we get to the next magnitude of agent scale.

Thesis

Source control is solved when every commit, landed or in flight, lives in one place: the commit cloud. Commits are created server-side, synced to any client that needs them, and computable by the system itself. Git stores history on laptops and negotiates copies between them. We store commits in the cloud and let clients ask questions. That is what gets us to the next magnitude of agent scale.

Where we are

We run a massive, fast-moving Git monorepo, kept alive with mirrors, shallow clones, sparse checkouts, and snapshot seeds, each a workaround for a design that assumed every client holds the whole repository. But the deeper problem is where commits live. In git, a commit exists on one machine until someone pushes it. Unpushed work is invisible: CI cannot test it, reviewers cannot see it, an agent cannot pick it up. Work in flight, which is most of the work, and nearly all agent work, lives outside the system that is supposed to manage it. Agents run in sandboxes and spend their time cloning, pushing, and re-cloning just to move commits between the places work happens.

The bet

Anthropic’s Scion is the proof of the model: clients always online, commits created server-side, everything else derived from that.1 The piece that makes it cohere is the commit cloud.

  • Commits are born in the cloud. A commit is created server-side, as a changeset in an append-only log with content-addressed pointers into blob storage. There is no push step, because there is nowhere to push from. The cloud is the first and only home a commit has.
  • The cloud holds in-flight work, not just main. Drafts, stacks, half-finished agent runs: all first-class cloud commits from the moment they exist, visible to CI, to review, and to other agents, subject to access control. A human can hand a change to an agent, or take one over, because the change lives in the cloud and not on someone’s laptop.
  • Clients sync, they do not clone. A working copy is a sparse, virtualized view over cloud state. Moving machines is a sync. So is an agent sandbox starting up: no multi-gigabyte fetch, no seeds falling behind the tip.
  • Everything else is derived data over the cloud. Blame, path history, ancestry, and indexes for search and code intelligence are computed from the cloud’s commit log, behind an API. No fully materialized copy of the repo anywhere, and no local repo needed to answer a question about one.

The cloud is also what makes the rest of the agent-scale agenda possible at all. Landing changes without a merge queue needs the server to hold every open change. Running code mods at merge time needs to compute over all of them. Indexing every change the moment it exists needs a creation event to trigger on. None of that works if commits live on laptops. All of it falls out once commits live in the cloud.

What we build

  1. The commit cloud itself: an authoritative, replicated changeset log over content-addressed blob storage, holding landed and in-flight commits alike.
  2. Server-side commit creation and a sync protocol: clients sync state instead of pushing objects, with stable change IDs across rewrites.
  3. Sparse, virtualized working copies over cloud state, so a checkout or a sandbox startup costs seconds.
  4. The source-control API over the cloud, answering blame, history, diff, and ancestry with no local repo, plus access control down to the directory, covering in-flight work too.

Open questions

  • The offline story. Git’s best property is the one we are giving up. How much local capability do we keep for the plane case, and is the honest answer just “less than you want.”
  • Sync conflicts: two clients rewriting the same change at once, and what the cloud’s conflict semantics should be.
  • Visibility defaults for in-flight work: who can see a draft, and whether agent work defaults to visible or private.
  • The migration path for a monorepo this size, and the long tail of tools that speak git and will keep speaking it for years.
